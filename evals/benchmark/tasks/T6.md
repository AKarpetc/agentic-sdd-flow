# ORD-47 — Order transitions with history

Orders move through their statuses by hand today and nothing records who moved them. Add an explicit
transition endpoint, an audit history, and one place that decides whether a transition is legal.

Acceptance criteria:
1. `POST /api/orders/{id}/transitions` with body `{"to":"<status>","requestId":"<string>"}` →
   `200 OK` with JSON `{"orderId": <long>, "status": "<new status>"}` when the transition is legal, and the
   new status is persisted (a later `GET /api/orders/{id}` shows it).
2. The legal transitions are exactly: `Placed → Paid`, `Paid → Shipped`, `Placed → Cancelled`,
   `Paid → Cancelled`. Every other pair is illegal → `409 Conflict` with a ProblemDetails body whose
   `title` says why. In particular a `Shipped` order can no longer be cancelled.
3. An unknown order id → `404 Not Found`. A `to` value that is not one of the statuses → `400 Bad Request`
   with a ProblemDetails body.
4. **Idempotency**: repeating a request with the same `requestId` for the same order returns `200` with the
   same body as the first call and adds no second history entry, whether or not the status changed in
   between.
5. `GET /api/orders/{id}/history` → `200 OK` with a JSON array, oldest first, of the transitions applied to
   that order: `[{"from":"<status>","to":"<status>","requestId":"<string>"}]`. An order that never moved
   returns `[]`.
6. The transition rule lives in **one** place in the service layer, and the existing
   `OrderService.CanCancelAsync` is expressed through it — the rule must not exist twice in the codebase.
7. Unit tests cover the legal and illegal transitions, the idempotent repeat and the history, and pass with
   `dotnet test`.
8. Commit messages are `ORD-47: <Description>`.
