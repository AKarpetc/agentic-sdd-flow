# 0.2.8 — one flow per size of change

What changed after the [0.2.7 benchmark](benchmark-2026-09-findings.md), why, and how to prove it worked.

The 0.2.7 measurement said three things at once: the plugin's tests and review are worth paying for,
about half of what it charges is overhead, and the defects its review finds never get fixed. The
0.2.8 answer is not "make the flow cheaper" — it is **make the flow's size a decision**, and then
close the two leaks that made the expensive version worth less than it cost.

## 1. The route is chosen, not assumed

`dotnet-feature` now sizes the change before it starts and says which route it took. The rubric is five
questions — blast radius, surface, data, reach, how much of the *what* is already decided
([sizing.md](../skills/dotnet-feature/references/sizing.md)) — answered from the brief plus at most one
repository lookup.

| Tier | Route | Gates kept | Gates dropped |
|---|---|---|---|
| `quick` | the superpowers flow (brainstorming → test-driven-development) in the session, no plugin agent | the rules contract and the write gate (hooks), the tests the flow writes itself | every plugin agent: implementer, tests-writer, reviewer, workflow |
| `mix` (B) | the superpowers flow, then `dotnet-sdd` `mode: 'review'` on the finished branch | one whole-branch review at full effort, the verifier on every finding, one fix wave, the defect floor | the plan, the plan review, the per-task implement/tests/review loop |
| `light` | `dotnet-sdd` `mode: 'light'` | tests per task, one whole-branch review + one fix wave | plan review, per-task review/verify/fix loop |
| `standard` | `dotnet-sdd` as before | everything | the second plan review (`skipPlanReview: true` once the skill's reviewer approved) |
| `deep` | `architecture-design` then `standard` | the panel, the design review | with `scope: 'compact'`: four judge passes, the threat model unless a trust boundary moves, the data review unless a store is touched |

Two guards keep the gate honest: **one tier up, never two** (a brief that merely sounds big is not
evidence — `deep` needs a concrete yes on surface, data or reach), and **escalation is upwards only**,
on evidence produced during the run (an unexpected file, a Debug phase, a `critical` in the final review).
`--tier` forces a route when the user knows better.

The 0.2.7 T4 failure is exactly what this prevents: a one-service change took the full design panel,
spent minutes 3–72 producing 48 000 words, and delivered no code inside the budget.

## 2. Defects reach the code

Three changes, all in the same direction — a finding that describes a real failure cannot be filed away
as taste:

- Every finding now carries `kind` — `defect` | `convention` | `style` — next to its severity, and the
  review skill states a **severity floor**: a `defect` is never below `important`, whatever section it
  was written in. Blocking is decided by severity *or* kind, so a race written up under "Refactoring
  Suggestions" can no longer be deferred for ever.
- `findings-verifier` returns `severityAdjustment`: having read the code, it may raise a `minor` it can
  actually reproduce (and lower one it cannot reach). Raising is a claim — the reachable path goes in
  `evidence`.
- A minor defect never opens a fix round of its own. It **rides along**: appended to the next fix round's
  list at no extra round, and otherwise fixed in the final wave, followed by a scoped `effort: low`
  "addressed?" check. Whatever is still open is parked as `unstable`, not silently dropped.

On T1–T3 this is what would have closed the two real bugs both arms shipped — the check-then-act race on
concurrent cancels and the `int` overflow in paging arithmetic. The review already found them.

## 3. The overhead is gone, not the quality drivers

| Cut | Where | Was |
|---|---|---|
| No `git rev-parse` agents | the SHA rides on `report.headSha` / `tests.headSha`; the analyze agent returns `baseSha` in the Bash call it already makes | 4 dispatches per task, **35 % of the workflow's tokens** |
| One plan review | `skipPlanReview: true` from the skill once its own reviewer approved | the same plan reviewed twice, ≈ 3–4 min |
| Test-only and verification-only tasks skip the implementer and the per-task review | task `kind` from the Analyze phase | a full implement → review cycle for a task with no production diff |
| Round-0 review at `effort: 'low'` when the tests are green and the task touches ≤ 5 files | the per-task review loop | full-effort review of every green task; the whole-branch final review still runs at full effort |
| A `tests-writer` brief that forbids padding — no tests for untouched members, record equality, DI registration or framework binding | `testsPrompt` and the agent's step 4b | blind auditors counted ≈ 40 % of the plugin's tests as volume |

What is deliberately **not** cut: the `WebApplicationFactory` endpoint tests (the baseline never writes
them — 0 % `Program.cs` coverage in every 0.2.7 baseline tree), the whole-branch final review, the
verifier in front of the fix loop, and the rules gate.

## 3b. A contradiction is reconciled, not guessed

A brief that says one thing while the code, a test, a CI assertion, an ADR, a doc, a comment or a
consumer note says another is the case where an agent does the most damage with the best intentions:
it "fixes" a behaviour a consumer depends on because the ticket said so, or keeps a bug because a
comment called it intended. 0.2.8 adds `evidence-reconciler` (read-only) and a **Reconcile** phase:

- the implementer stops before changing a contested behaviour and returns the contradiction (claim,
  observed `file:line`, sources) instead of picking a side;
- the reconciler enumerates every source and weighs it — **executed** (tests, CI assertions, consumer
  parsers) > **decided** (ADRs, consumer contracts, incident-tied changelog) > **descriptive** (docs, XML
  docs, comments, commit messages) > **intent** (the brief); independence and recency break ties; a comment
  that disagrees with the code it annotates is evidence of drift, not of truth;
- `brief` → the code is fixed at the root and the stale comment/doc corrected in the same commit;
  `code` or `undecided` → the workflow returns `status: 'contradiction'` with the evidence table and the
  user rules (`args.truth[taskId]`); a record is never rewritten to match a ticket;
- `docs-sync` reports a record that disagrees with the diff as `contested` instead of editing it, and
  `plan-reviewer` and the review skill file a plan or a diff that flips a recorded behaviour without
  touching the record as `important`.

The benchmark's conflict pair (T8: the records back the brief; T9: the same brief, the records back the
code) measures exactly this in both directions — see the benchmark README.

## 3c. Where the 73 minutes went — the bottleneck, measured

The T6 (complex) pair is the sharpest datum of the 0.2.8 run: **superpowers $4.30 / 7.4 min, plugin
`standard` $31.51 / 73.4 min, both 10/10 acceptance, both closing the transition race, +0 convention
violations either way.** So the question is not "is the plugin better" but "what are the 66 extra
minutes made of".

| Signal | plugin `standard` | superpowers |
|---|---|---|
| `duration_api_ms` ÷ wall | 71.6 min of 73.4 (**97.6 %**) | 6.9 min of 7.4 (93 %) |
| agent dispatches | 26, strictly serial | 0 — one session, 66 turns |
| `dotnet` invocations recorded in reports | 9 | comparable |
| Roslyn | bound correctly on the first call (`get_project_graph` returned both projects) | not used |
| agent time by role | reviewer 16.3 min (26 %), implementer 16.2 (26 %), tests-writer 15.1 (24 %), **plan-reviewer 11.9 (19 %)**, verifier 2.2 (3 %) | — |

**It is not I/O.** Nothing was waiting on builds, tests, the network or a mis-bound Roslyn: 97.6 % of the
wall clock is model inference. The 66 minutes are the cost of **re-establishing context 26 times** — every
agent starts empty, reads the rules contract, reads its skill (the reviewer reads a 326-line SKILL.md plus
the checklist, seven times over), reads the code again, then acts. Per tool call the agents ran at 4–20 s;
the single-session baseline ran at ~6.7 s per turn. The rate is the same. The volume is 10×.

Which tells us which levers exist and which are fake:

- **Real: fewer, larger agents.** A plan of five tasks × (implementer + tests-writer + reviewer + verifier)
  is 26 dispatches; the same branch reviewed once is one. This is what routes A and B are.
- **Real: a scoped second pass.** `plan-reviewer` ran twice at full depth (7.0 + 4.8 min) on the same
  plan — 19 % of the run to review a document that had already been reviewed.
- **Half-real: parallelism.** Running independent plan tasks concurrently would cut wall clock but not
  cost, and it is unsafe in one working directory — two implementers committing to the same branch will
  interleave. It needs a worktree per task; not attempted here.
- **Fake: "make the agents faster".** They are not slow. The runner is not the problem, the SDK is not the
  problem, `dotnet` is not the problem. Anything that keeps 26 sequential contexts will keep this number.

## 4. Fixed from the run itself

`Workflow` args arriving as a JSON string are parsed in both scripts; the implementer is told, in the
agent and in every workflow prompt, to commit **on the checked-out branch** and never to create one or
write outside `projectDir`; `dotnet-feature` says not to resume a run after editing the plan (the cached
rejection would be replayed).

## 5. Expected effect — a projection, not a measurement

Derived from the 0.2.7 phase-by-phase share of tokens and wall clock. **Nothing here has been measured
yet**; the point of writing it down is that the re-run either confirms it or does not.

| Task | 0.2.7 | 0.2.8 projected | Route |
|---|---|---|---|
| T5 (simple) | not measured; would have taken the full flow | ≈ $2–4, 4–8 min (measured 2026-09-07 on Opus 5: superpowers flow $2.23 / 3.8 min, the gate's `light` mis-route $7.38 / 16 min, identical trees) | `quick` |
| T1 (medium) | $31.95, 34 min | ≈ $8–14, 12–20 min | `light` |
| T2 / T3 (medium) | $46.91 / $39.72 | ≈ $18–25, 25–35 min | `standard` |
| T6 (complex) | not measured | ≈ $22–30 | `standard` |
| T4 / T7 (vague) | 0/8 at the 90-minute cap | delivered inside the budget | `standard` |

The claim to test is **not** "the plugin got cheaper". It is: *cost per run climbs with the class of the
task, and the quality gap the 0.2.7 audit found — endpoint tests, branch coverage, contract-compliant
tests, defects actually fixed — survives the cuts.*

## 6. How to verify

```
python3 evals/benchmark/run.py --class simple --class complex --out results/bench-<date> --workers 1
python3 evals/benchmark/run.py --task T1 --task T4 --task T7 --out results/bench-<date> --workers 1
python3 evals/benchmark/report.py results/bench-<date> > results/bench-<date>/report.md
```

Read, in this order:

1. **The `route` column** against the expected tier per task. A `standard` route on T5 means the sizing
   gate failed, and no cost number below it means anything.
2. **The *By task class* table** — cost per run must climb simple → medium → complex. If it is flat, the
   tiering is decorative.
3. **`tests written` with the `✅http` marker** — the quality driver that justified the plugin in 0.2.7.
   If the padding rule also removed the endpoint tests, the cut went too far.
4. **The planted-bug column and the two known defects** (T2's concurrent-cancel race, T3's paging
   overflow) — the point of §2 is that a re-review of the final tree finds them closed.
5. Only then cost and wall clock.

Both arms must be re-measured: the baseline arm's instruction changed in 0.2.8 (it may now scale itself
down when brainstorming calls a change bounded, instead of being forced through the full flow), so the
0.2.7 baseline numbers are no longer comparable.

## 7. What this does not answer

- **`deep` is untested.** The benchmark fixture is one solution with no data store and no external
  contract, so no task in it can honestly demand the design pipeline. Measuring the `deep` route — and
  whether `scope: 'compact'` keeps its value — needs a multi-project fixture.
- **One run per (task, arm) is still a sample.** Routing is a judgement call made by a model; whether the
  gate is *stable* needs repetitions, not one green column.
- **The gate can be wrong in the expensive direction and look right.** A `standard` route on a `light`
  task still passes every acceptance check — only the cost column shows it. That is why the class table
  is the first thing to read.
